# 規則描述模型

本文件定義「海大各系修業規定怎麼被記錄」的格式，是人類可讀性與機器可檢核性的共同規格。機器版見 [rule-bundle.schema.json](rule-bundle.schema.json)，可執行範例見 [examples/](examples/)，可行性驗證見 [spike/](spike/)。

適用範圍：日間學制學士班（含進修學士班）的畢業規則。碩博士班規則結構相近，但學位考試與論文條件不在本版範圍。

---

## 1. 為什麼要分三層

一條畢業規定同時要滿足兩種讀者：**系所管理員要看得懂**（能對照原文、判斷有沒有抄錯），**引擎要算得動**（能取出學分、類別、上限）。把兩件事塞在同一層，通常兩邊都做不好，所以拆成三層：

```
來源卡 Source ──1:N──▶ 條文卡 Clause ──1:N──▶ 條件節點 Requirement
（哪份文件）          （原文怎麼寫）          （機器怎麼算）
```

| 層 | 給誰看 | 必須有 | 不可以有 |
| --- | --- | --- | --- |
| 來源卡 | 所有人 | 名稱、URL、版本、頁碼定位、取得時間、雜湊 | 解釋、推論 |
| 條文卡 | 系所管理員、學生 | 原文逐字、定位、白話說明 | 原文沒有的門檻 |
| 條件節點 | 引擎、測試 | 型別、門檻、課程集合、來源條文 | 未標註來源的數字 |

**核心原則：條件節點只能引用條文卡，不能憑空出現數字。** 任何節點若找不到來源條文，結構驗證就會失敗（spike 已實作此檢查）。

## 2. 識別碼規則

| 對象 | 格式 | 例 | 穩定性 |
| --- | --- | --- | --- |
| 規則包 | `{系所}-{入學年}-{學制}` | `cse-113-day` | 不變 |
| 版本 | `bundleId@versionNo` | `cse-113-day@3` | 發布後不可改寫 |
| 來源 | `S{年度}-{序號}` | `S113-02` | 不變 |
| 條文卡 | `C{序號}` | `C02` | 同一規則包內不變 |
| 條件節點 | `R{序號}` | `R07` | **跨版本穩定**（個人覆蓋靠它延續） |

條件節點的 ID 不能因為排序調整而重編；刪除節點時保留 ID 並標記 `retired`，避免學生的個人覆蓋錯位。

## 3. 條文卡欄位

| 欄位 | 必填 | 說明 |
| --- | --- | --- |
| `clauseId` | ✓ | 規則包內唯一 |
| `sourceId` | ✓ | 指到來源卡 |
| `locator` | ✓ | 頁碼、條號、表格欄名，例如「頁 1 第二條」「檢核表（Ⅰ）博雅」 |
| `text` | ✓ | 原文逐字或最小改寫；**不得加入解釋** |
| `reading` | | 白話說明，只能把原文講清楚，不能放寬或加嚴 |
| `status` | | `verified`／`pending`／`conflict`，預設 verified |
| `note` | | 待確認原因、版本差異 |

> 實務上最容易出錯的是把 `reading` 寫成新的規定。審核時應以 `text` 為準，`reading` 只作為輔助。

## 4. 條件節點六型

| 型別 | 用途 | 主要欄位 | 113 資工例子 |
| --- | --- | --- | --- |
| `total` | 畢業總學分 | `min` | 至少 135 |
| `pool` | 學分池下限 | `poolId`、`min` | 共同教育 28、系訂必修 50 |
| `credits` | 不消耗額度的子集合 | `selectors`、`min`、`courses` | 系內 46、核心 12、博雅 14 |
| `courseSet` | 指定課程群組 | `mode`（all／any／minCount／minCredits）、`courses` | 18 門指定必修 |
| `status` | 非學分條件 | `statusKey`、`source` | 英文門檻、操行、體育四學期、游泳 |
| `and`／`or` | 組合 | `children` | 替代路線、多選一 |

`credits` 與 `pool` 的差別是本案最容易誤解的地方：

- `pool` **消耗**採計額度：一門課只會被一個池認領（由 `precedence` 決定），所以不會重複計入總學分。
- `credits` **不消耗**額度：核心 12 學分是從系內 46 裡「再看一次」，不是額外 12 學分。

這個區分讓「核心 ⊆ 系內 ⊆ 選修」的包含關係可以直接表達，不需要在資料上複製學分（spike 第 2、8 案例即驗證此事）。

## 5. 採計配置：池、優先序、上限

```jsonc
"allocation": {
  "totalMin": 135,
  "precedence": ["ce", "req", "inner", "outside"],   // 同課符合多池時的歸屬順序
  "pools": [
    { "poolId": "inner", "min": 46, "selectors": ["owner:own", "tag:program"] }
  ],
  "caps": [
    { "capId": "CAP-COLLEGE", "selectors": ["tag:collegeNonProgram"], "max": 6, "clauseId": "C03" }
  ]
}
```

上限有三種語意，本模型分開表達：

| 語意 | 表達方式 | 例子 |
| --- | --- | --- |
| 整池上限 | `pool.max` | 電資學院非上述學程「以 6 學分為上限」（亦可寫成 cap） |
| 單課上限 | `pool.perCourseCreditsMax` | 體育室選修每門 1 學分，只認 1 學分 |
| 跨池／跨類上限 | `caps[]` | 額外共同教育抵外系至多 8、博雅各子領域至多 4 |

`caps[].scope = "pool"` 時只限制指定池；預設 `"total"` 限制總認列量。上限是**認列**上限而不是修課上限，超過部分仍可修課，只是不計入該條件。

## 6. 三態與整體結果

| 節點狀態 | 意義 | 來源 |
| --- | --- | --- |
| `met` | 已達標 | 學分足夠、課程完成、狀態已認定 |
| `notMet` | 確定未達標 | 學分不足、缺必修 |
| `unknown` | 尚未確認 | 缺資料、未認定、未建模 |

整體結果：任一必要條件 `notMet` → **尚有條件未完成**；否則有 `unknown` 或有未解衝突 → **尚有條件待確認**；全部 `met` 且無衝突 → **依目前資料與規則已滿足**。

**未解衝突必須擋住「已滿足」。** 113 資工的電子商務學程採計（修業規定四門排除 vs 檢核表八門白名單）就是這種情況：即使其他條件全達標，結果也只能停在「待確認」（spike 第 2、7 案例）。

## 8. 多系所驗證矩陣

用三個結構差異大的來源驗證格式是否夠用（不是完整登錄，是「能不能表達」）：

| 差異點 | 資工 113 | 商船 115 | 機械與機電 | 模型表達方式 | 結果 |
| --- | --- | --- | --- | --- | --- |
| 總學分 | 135 | 136 | — | `total.min` | ✅ |
| 三池結構 | 28／50／57 | 28／70／38 | — | `pools` + `precedence` | ✅ |
| 子集合（核心⊆系內） | 核心 12⊆系內 46 | 管理級 18⊆主領域 38 | — | `credits` 不消耗額度 | ✅ |
| 領域／學群選修 | 學程白名單（4 個學程） | 航行／船務領域建議必選（19／14） | — | `credits`+`tag`；「建議」以 `required:false` 標記 | ✅（建議性質需人工標記） |
| 跨類上限 | 電資學院 6、額外共同教育 8 | 外系相關課程 8 | 體育計入以 1 學分為限、通識選修以 2 學分為限 | `caps[]`／`perCourseCreditsMax` | ✅ |
| 子領域上限＋下限 | 博雅各領域 ≤4、跨域永續 ≥2 | — | — | 四個 `caps` + 一個 `credits` | ✅ |
| 非學分條件 | 英文、操行、體育四學期、游泳 | 操行、海上實習（待確認） | — | `status` 節點 | ✅ |
| 抵免／免修 | 英語抵免、游泳免修 | — | — | `status` 值 `transfer`／`waived` | ✅（spike 第 6 案例） |
| 版本衝突 | 電子商務四門 vs 八門 | 主領域 36 vs 38 | — | `conflicts[]` 擋住完整達標 | ✅ |
| 多種入學年度並存 | 113／114／115 各自一份 | 同 | 同 | 一個年度一個 `bundleId` | ✅ |
| 雙主修／輔系加修 | 外系生加修資工 | — | — | 需 `scope.studentType` 擴充 | ⚠️ 本版未建模 |
| 學年課上下學期連動 | — | — | 電機類「全學年都不算學分」 | 需「課程群組連動」規則 | ❌ 表達不了，列待確認 |
| 擋修／先修鏈 | 50 分擋修 | — | 先修順序 | 由規劃模組處理，非畢業判定 | ⚠️ 範圍外（另立先修模型） |

**結論：** 三個系所的主要結構差異都能用同一份 schema 表達，且不需要為個別系所寫程式碼。已知表達不了的是「學年課上下學期連動」這種跨課程連動規則，以及雙主修身分——兩者都已列入待確認，不會假裝支援。

## 9. 撰寫規範（人與 AI 共用）

一條新規定進來時，照這個順序做：

1. **建來源卡**：下載官方檔、記 URL／版本／頁碼、算雜湊。
2. **切條文卡**：一條一款一張卡，`text` 逐字，`reading` 只翻白話。
3. **判斷型別**：有學分門檻 → `total`／`pool`／`credits`；列課程名稱 → `courseSet`；有「至多」「為限」→ `caps`；無學分 → `status`。
4. **確認包含關係**：問「這是額外學分，還是子集合？」前者 `pool`，後者 `credits`。
5. **標上限**：把「至多 N」寫進 `caps`，不要寫進 `min`。
6. **標衝突**：兩份文件寫法不同就建 `conflicts`，不要自己選一個。
7. **寫測試案例**：至少一個達標、一個不足、一個上限或重複案例。
8. **送審**：結構驗證通過才能進入審核佇列（見系統設計文件第 6 節）。

AI 產初稿時只能做 1～5 步；第 6 步以後必須人工，且 AI 不得自行決定衝突的採計方式。

## 10. 已知限制（誠實清單）

1. 「至多」「至少」以外的模糊語意（例如「原則上」「得視情況」）無法自動化，只能建 `status` 並由人認定。
2. 跨課程連動（學年課上下學期、正課與實習綁定）尚未支援。
3. 課程等價與替代（舊課號換新課號）需要另一份「課程對應表」，本模型只留 `allowEquivalent` 旗標。
4. 個人抵免結果依校方認定，模型只存「已認定／未認定」，不重算認定過程。
5. 同課號在大學部與研究所的抵用互斥（113 資工 R33）需在資料層標記修課層級，屬資料整合工作。
