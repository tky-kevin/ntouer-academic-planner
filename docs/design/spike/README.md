# 規則引擎可行性 spike

**這不是產品程式碼。** 目的是用最小實作回答一個問題：規則包格式能不能表達真實條文中的採計上限、重複採計、抵免／免修、例外衝突與多系所差異，並算出可追溯的結果。

## 執行

```bash
node docs/design/spike/run-cases.mjs
```

需要 Node 18 以上（只用 `node:fs`、`node:path`、`node:url`，無外部套件）。

## 內容

| 檔案 | 作用 |
| --- | --- |
| `rule-engine.mjs` | 規則包結構驗證 `validateBundle` 與檢核 `evaluate` |
| `run-cases.mjs` | 27 項案例與斷言，涵蓋 9 組情境 |

## 引擎做了什麼

1. 依情境篩選紀錄（已完成 < 修課中 < 計畫）
2. 同課去重（及格優先，其次抵免／免修、修課中、計畫）
3. 依 `precedence` 逐池認領，套用 `pool.max`、`perCourseCreditsMax`、`caps`
4. 計算各池與總學分（同一門課只貢獻一次）
5. 由下往上判定六型節點與 `and`/`or`，輸出 `met`／`notMet`／`unknown`
6. 匯總整體結果；未解衝突會擋住「已滿足」

## 已知限制（刻意不做的部分）

- 無資料庫、無 API、無權限檢查、無多使用者。
- 無課程目錄；`courseCode` 直接當鍵，正式版需接課號對應表。
- `caps` 每次計算重新起算，尚未處理「同一上限跨多個條件共享額度」的情境。
- 不處理學年課上下學期連動、雙主修身分、先修鏈（見設計文件第 12 節）。

這些限制都在[規則描述模型](../rule-model.md)第 10 節與[系統設計文件](../system-design.md)第 12 節列出，正式實作時必須補上並保留本 spike 的案例作為回歸測試。
