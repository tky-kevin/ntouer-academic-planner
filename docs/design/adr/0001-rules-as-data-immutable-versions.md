# ADR-0001：規則即資料，發布後版本不可變

Extends: system-design.md §2（設計原則）、§4.2（版本與識別）、§7.1（發布狀態機）、§9（資料模型）

- **狀態**：Accepted（已定案，2026/11/16）
- **日期**：2026/11/16
- **決策者**：第七組（tky-kevin 彙整）
- **對應需求**：FR-11、FR-12、FR-17、FR-18、NFR-01、NFR-05、NFR-06
- **對應驗收**：TC-20（覆蓋遷移）、TC-30（重複採計）、TC-33（多系所）、TC-34（稽核追溯）
- **取代**：取代 I1「規則寫在程式碼」的作法（`src/data/testRules.ts` 的 12／6／6）

## 背景

I1 把三條學分門檻寫死在 `src/data/testRules.ts`，引擎 `src/engine/checkCredits.ts` 直接讀它。這個作法在 I1 夠用，但在 I2 會撞到三件事：

1. **FR-17 明訂「新增系所不得修改引擎程式碼」。** 規則寫在程式碼裡，每加一個系所或入學年度就要改程式、跑測試、重新部署。
2. **FR-12 明訂「發布版本形成不可原地覆寫的歷史快照」。** 程式碼裡的規則沒有版本概念；學生三天前看到的結果無法重現。
3. **FR-18 要求每次發布留下內容雜湊與變更摘要。** 沒有唯讀快照就沒有「審的是哪一版」可以證明。

同時，規則的維護者不是工程師：他們看得懂官方 PDF 的條文，但不該被要求改 TypeScript。

## 決策

1. **畢業規則一律以「規則包」表示**，格式見 [rule-bundle.schema.json](../rule-bundle.schema.json) 與 [rule-model.md](../rule-model.md)。引擎只認 schema 的六型節點（`total`、`pool`、`credits`、`courseSet`、`status`、`and`／`or`）與採計配置（`pools`、`precedence`、`caps`、`conflicts`），**不知道任何系名**。
2. **一個（系所 × 入學年度 × 學制）＝ 一個 `bundleId`**，例如 `cse-113-day`。發布產生 `versionNo`，`bundleId@versionNo` 為唯讀快照。
3. **不可原地修改。** 要改規則＝從目前版本複製成新 `draft`，走完 結構驗證 → 測試案例 → 審核 → 發布 才成為新版本。舊版本改標 `superseded`，**不刪除、不改寫**（FR-12、FR-18）。
4. **每次檢核的輸出綁定 `versionId`。** 學生的結果、個人覆蓋與稽核紀錄都能回指同一個版本號與內容雜湊。
5. **條件節點 ID 跨版本穩定。** 節點不再使用時標 `retired` 而不是重編號，避免學生個人覆蓋在新版錯位（TC-20）。

## 為什麼不是其他作法

| 替代方案 | 為何不採用 |
| --- | --- |
| 規則繼續寫在程式碼（I1 現況） | 直接違反 FR-17 的「新增系所不改程式碼」；非工程師無法維護；沒有版本快照，FR-12、FR-18 無法驗收。 |
| 每種節點開一張關聯表（關聯式建模） | 六型節點再加 `and`／`or` 組合，會變成 EAV 式的深層 join；每加一種節點就要 schema 遷移；「整份版本」的原子快照與內容雜湊難以表達。 |
| 規則包存一般文字欄位（不驗結構） | 引擎要自己防禦格式錯誤，錯誤會延後到檢核時才爆；FR-17 要求「錯誤欄位不得形成可發布版本」。 |
| **規則包 JSON + 發布即凍結（採用）** | 引擎資料驅動、新增系所只加資料；版本與雜湊可直接驗證；維護者改的是資料不是程式。 |

## 後果

**好處**

- 三系所共用同一支引擎：資工 113、商船 115、機械與機電的差異全在資料（[system-design.md §4.1](../system-design.md)）。
- 版本不可變讓「同一輸入必得同一結果」（NFR-01）有可驗證的機制，而不只是承諾。
- 稽核可以證明「審的是哪一版」：內容雜湊存在版本與每一次動作紀錄上。

**代價與風險**

- **`payload` 會重複儲存整份規則包**（每次發布一份），換來的是唯讀與可回溯。以 46 條規模估算，單份為數十 KB 級，可接受。
- **diff 要自己算。** 資料庫不會給「這一版改了什麼」，需以結構比較產生（節點 id、型別、門檻、課程集合、組合關係），見 system-design.md §7.2。這也是刻意設計：不依賴 AI 語意判斷。
- **欄位查詢要靠投影表。** jsonb 內的條文不利直接查詢與索引，需 `rule_sources`／`rule_clauses` 兩張表輔助（ADR-0002）。
- **schema 演進要相容。** 節點型別若新增，舊版本仍必須可讀；schema 版本號與 `retired` 機制要同步維護。

## 驗證方式

- 結構驗證器擋下缺條文參照、selector 格式錯誤、池參照不存在的規則包（spike 案例 1）。
- spike 27 項全數通過（`node docs/design/spike/run-cases.mjs`），其中案例 4～7 覆蓋上限、重複採計、抵免／免修、未解衝突。
- TC-33：同一引擎載入資工 113 與商船 115 都算得對，不改程式碼。
- TC-34：任一結果可回查版本、條文定位、審核者與發布時間。
