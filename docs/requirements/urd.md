# NTOUER Academic Planner 使用者需求文件

- **專案名稱**：海大智慧修課與畢業規劃系統
- **版本**：1.3
- **修訂日期**：2026/11/16
- **文件用途**：供使用者、教師與團隊確認使用者角色、目標及需求範圍。
- **配套文件**：[NTOUER Academic Planner 系統需求文件 v0.9](srs.md)

## 1. 文件定位與使用者需求概述

本文件說明「誰需要完成什麼，以及為什麼需要」。系統的具體行為、權限判斷、錯誤情境、資料採計規則、量化品質條件及驗收案例，統一記載於配套系統需求文件。本文件的 AP-UR 編號沿用原使用者需求，兩份文件的對應關係見系統需求文件第 13 節。文件版次各自管理，無須與系統需求文件相同。

海大學生需要整合分散的修課紀錄與畢業規定，清楚掌握已完成與尚缺的畢業條件，並依剩餘需求安排未來學期的課程。學生需要取得與修正個人資料、查看畢業進度、搜尋合適課程、保存修課計畫，以及比較不同修課情境下的結果，減少人工核對資料與規劃課程的負擔。

規則維護者需要依官方來源建立及確認畢業規則，並依系所授權發布適用版本，讓學生了解檢核結果的依據、資料時間與適用範圍。

首批 MVP 適用對象為 113 學年度入學的海大資訊工程學系學生。以下描述預期需求，不表示功能已全部實作；系統結果供自主規劃參考，不取代學校正式畢業審查。

## 2. 使用者與目標

| 使用者 | 使用目標 |
| --- | --- |
| 學生 | 掌握個人畢業進度，補充或修正資料，安排並調整未來修課計畫。 |
| 系所管理員 | 為所屬系所建立、確認、測試及發布畢業規則，並保留來源與審核紀錄。 |
| 系統管理員（最高權限） | 維護系所清單與來源、指派或移除系所管理員，並在系所尚無管理員時代理發布。 |
| Demo 操作者 | 使用模擬資料展示基本學分檢核，理解資料變化如何影響結果。 |

權限層級由高至低為系統管理員、系所管理員、學生：系所管理員只能處理被指派的系所，學生只能讀取已發布規則與自己的資料。前版所稱「開發者」自本版起統一改稱「系統管理員」。「規則維護者」為系統管理員與系所管理員在規則維護情境下的統稱；具體發布權限由系統需求文件定義。Demo 操作者是第一次迭代的展示角色。

## 3. MVP 使用者需求

以下以使用者角色、希望完成的工作及其目的表達需求。MVP 為產品的必要範圍，不等於第一次迭代須完成全部項目。

| 編號 | 使用者需求 |
| --- | --- |
| AP-UR-01 | 作為學生，我希望以 Google 帳號登入，以便持續存取自己的設定、修課資料與計畫。 |
| AP-UR-02 | 作為學生，我希望在需要時同步教務系統資料，以便減少手動整理修課紀錄的時間。 |
| AP-UR-03 | 作為學生，我希望查看適用於自己系所及入學年度的畢業條件與缺額，以便知道還需要完成哪些課程及門檻。 |
| AP-UR-04 | 作為學生，我希望比較目前已完成、本學期課程也通過，以及再加上規劃課程都通過的進度，以便判斷修課安排是否能補足缺額。 |
| AP-UR-05 | 作為學生，我希望新增、修正、排除或恢復個人修課紀錄，以便反映抵免、免修或資料缺漏等實際情況。 |
| AP-UR-06 | 作為學生，我希望自行設定或取消個別畢業條件的完成狀態，以便補充系統無法取得的資訊，例如英文門檻。 |
| AP-UR-07 | 作為學生，我希望依課程名稱或代碼搜尋課程並查看歷年開課資訊，以便找到適合安排的修課選項。 |
| AP-UR-08 | 作為學生，我希望從尚缺的畢業條件找到可對應的候選課程，以便縮小搜尋範圍。 |
| AP-UR-09 | 作為學生，我希望依學期加入、移動、移除及保存計畫課程，以便持續調整未來修課安排。 |
| AP-UR-10 | 作為學生，我希望知道計畫中正式班別的上課時間是否重疊，以便調整同學期的課程安排。 |
| AP-UR-11 | 作為規則維護者，我希望依官方文件建立、修改及預覽畢業規則，以便確認檢核依據與結果。 |
| AP-UR-12 | 作為具發布權的維護者，我希望發布及保留不同版本的規則，以便控制學生使用的條件並追溯變更。 |
| AP-UR-13 | 作為系統管理員，我希望指派或移除系所管理員，以便讓各系所的規則由授權人員維護及發布。 |
| AP-UR-18 | 作為規則維護者，我希望將官方 PDF 解析成可編輯的規則草稿，以便減少人工轉錄。 |
| AP-UR-22 | 作為系所管理員，我希望在發布前看到結構驗證結果、測試案例結果與與前版的差異，以便判斷是否核准。 |
| AP-UR-23 | 作為規則維護者，我希望同一套規則格式能套用到其他系所與入學年度，不必為每個系所另外開發，以便逐步擴大支援範圍。 |

## 4. 使用者期待的品質

本節保留使用者對可理解性、隱私、跨裝置操作及回應速度的期待。具體安全機制、畫面尺寸、效能門檻及測試環境由系統需求文件第 7 節定義。

| 編號 | 使用者需求 |
| --- | --- |
| AP-UR-14 | 作為學生，我希望理解結果是根據哪些資料與規則產生，以便判斷其適用性。 |
| AP-UR-15 | 作為學生，我希望個人資料與教務帳密受到保護，以便安心使用系統。 |
| AP-UR-16 | 作為使用者，我希望在手機及電腦上都能閱讀結果並完成主要操作，以便在不同情境下使用。 |
| AP-UR-17 | 作為學生，我希望檢核與搜尋及時回應，並清楚告知保存是否成功，以便連續調整計畫。 |

## 6. 第一次迭代的使用者需求

**AP-UR-21**：作為 Demo 操作者，我希望不登入即可選取模擬修課紀錄、執行基本學分檢核並查看結果，以便展示不同資料如何影響已取得學分與尚缺學分。

第一次迭代聚焦於以模擬資料展示基本學分檢核，協助團隊與教師確認操作流程及結果呈現。此階段不要求正式登入、AIS 同步或完整 113 資工畢業檢核。具體展示行為、測試資料、例外情境及完成條件見系統需求文件第 9.2 與 10.1 節。

## 7. 範圍界線

- **MVP 必要範圍**：個人身分與修課資料、畢業進度與情境比較、個人資料修正、課程查詢與修課規劃、衝堂資訊，以及規則維護與發布、官方 PDF 的 AI 規則草稿（經人工確認後才發布）。
- **優先擴充**：個人化候選計畫、已知先修條件等；產品完整範圍分類見系統需求文件第 2.4 節。
- **後續構想**：多方案比較、多學期最佳化與拖曳排課，未列入 MVP 必要需求。
- **範圍外**：代辦正式選課、保證未來開課、出具校方畢業資格認證。

學生的個人修正與條件設定僅供個人規劃，不代表修改共用畢業規則或取得校方認定。需求中的未知條件與資料限制，應讓使用者理解其對規劃結果的影響。
